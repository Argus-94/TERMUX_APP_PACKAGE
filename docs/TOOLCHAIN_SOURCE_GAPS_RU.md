# Почему полный Android toolchain пока не готов

## Короткий итог

Выполнена успешная сборка официальных исходников Gradle 9.8.2 в **host-only бинарную дистрибуцию** на Ubuntu 24.04 с Temurin JDK 25.0.4.1. Это подтверждает только создание и базовую проверку хостового Gradle. Это не Android/Bionic runtime, не `.deb`, не payload приложения и не разрешение кандидата или публикации.

Текущая подписанная 82-пакетная сборка остаётся test-only базой, а не полным Android build toolchain. В её runtime closure нет Gradle, Clang, SDK и NDK. Для Gradle source build использовался отдельно закреплённый бинарный bootstrap Gradle 9.8.1 — только как build tool на CI-хосте, не как результат source build и не как часть пакета. Пакетный recipe Gradle остаётся без изменений: `1:9.8.1`.

Инвентарь сверяет три dependency closure с неизменённым Termux source commit `505e06ef0c8dbd7611abfb90e9eb60826dcd01d7`. Это reference-only source metadata — не разрешение брать stock Termux пакеты/feed. Package build, candidate `.deb`, подписанный feed, APT simulation, Android install/runtime, сборка проекта и rollback остаются `NOT RUN`; qualification, candidate eligibility и production publication — `false`.

## Clang: возможен отдельный source-build, но текущий sysroot блокирует кандидат

Pinned upstream recipe содержит LLVM/Clang `21.1.8-3` и source archive `llvm-project-21.1.8.src.tar.xz` с SHA-256 `4633a236…6aa142`. Resolver строит reference closure из 15 пакетов и 19 dependency alternatives. Однако этот closure включает `ndk-sysroot`, а pinned recipe для него скачивает Google `android-ndk-r30-linux.zip` — готовый Linux-host distribution, не source-built Android/Bionic sysroot. Поэтому подписывать его как source-only Clang candidate сейчас нельзя. Для продолжения нужен независимо закреплённый разрешённый sysroot из исходников либо отдельное явное изменение границ задачи, затем полный build/package/ELF/license audit и только test-only signed APT simulation.

LLVM upstream отдельно публикует source archive и Linux binary releases; Linux Arm64 archive — это Linux-host binary, не Android/Bionic executable. См. [LLVM 21.1.8 release](https://github.com/llvm/llvm-project/releases/tag/llvmorg-21.1.8), [официальную документацию LLVM cross-build](https://llvm.org/docs/HowToCrossCompileLLVM.html) и закреплённые [Termux libllvm recipe](https://github.com/termux/termux-packages/blob/505e06ef0c8dbd7611abfb90e9eb60826dcd01d7/packages/libllvm/build.sh) и [clang split recipe](https://github.com/termux/termux-packages/blob/505e06ef0c8dbd7611abfb90e9eb60826dcd01d7/packages/libllvm/clang.subpackage.sh). Рецепты здесь использованы только для source metadata, не для скачивания готовых Termux `.deb`.

## Gradle: source build прошёл на хосте, Android/Bionic и package gates закрыты

Pinned Termux recipe остаётся `1:9.8.1` и указывает на `gradle-9.8.1-bin.zip` с закреплённым SHA-256 `dce76f55…b6dc01f`. Отдельный официальный source archive Gradle `9.8.2` — `gradle-9.8.2-src.zip`, SHA-256 `96c9aba0564daa2998f578b589eba9ae1f6656e368fde85f7132e05321bab553`, размер `88,741,444` байта. Его архивная структура, checksum и ZIP CRC были проверены.

В самом source archive committed wrapper указывает на готовый `gradle-9.8.1-bin.zip` без `distributionSha256Sum`. Wrapper **не запускался**. Вместо него CI отдельно скачал официальный Gradle 9.8.1, сверил фиксированный SHA-256 и официальный sidecar, проверил версию, затем напрямую вызвал этот executable как build-only bootstrap. Это проверенный бинарный bootstrap для host-сборки, а не «source-only bootstrap».

GitHub Actions run [40079300326](https://github.com/Argus-94/TERMUX_APP_PACKAGE/actions/runs/40079300326) завершился успешно на commit `08d20e16227ace186f2384c36c79c62df3ebc0e8` разрешённой ветки. Зафиксированный CI result — `SOURCE_BUILD_SUCCESS_HOST_ONLY`. На Ubuntu 24.04 / Temurin JDK 25.0.4.1 команда `:distributions-full:binDistributionZip -PfinalRelease=true` завершилась с кодом 0. CI evidence сообщает output `gradle-9.8.2-bin.zip`, размер `151,620,051` байт, SHA-256 `9928e360dc0832a3ddc39d705ff1728bc75667c846fda5660d448ac85cb91814`, успешные CRC и launcher version `Gradle 9.8.2`. Это хостовый результат сборки, не официальный Gradle release. Точная CI evidence сохранена в [`gradle-source-build-host-success.json`](evidence/gradle-source-build-host-success.json); run artifact ID `12554961307` доступен до 31 октября 2026 года: [скачать artifact](https://github.com/Argus-94/TERMUX_APP_PACKAGE/actions/runs/40079300326/artifacts/12554961307). Полная локальная копия дистрибуции не была получена: её скачивание оборвалось/обрезалось, поэтому независимая локальная проверка указанного output SHA и ZIP CRC не заявляется.

Source tree содержит `gradle/verification-metadata.xml` (SHA-256 `d9f3cb20522e9a7186160464f818b6635111c71b68d78084527a36e5180fa67e`; 88 компонентов и 98 артефактов с SHA-256/PGP metadata), а build settings используют Maven Central и Gradle Plugin Portal. Успешный CI run подтверждает выполнение source build с этими настройками, но сам по себе не доказывает hermetic/reproducible dependency closure для Android package candidate.

Результат **не** подтверждает ARM64/Bionic ELF и `DT_NEEDED` closure, native loader, file watching или daemon/app-private lifecycle; `androidBionicRuntime=NOT_VERIFIED`. Не создавались `.deb`, пакет, candidate, signed feed; не запускались APT simulation, Android/device tests, установка или сборка реального APK. Не публиковались feed/release и не открывались production gates. Source archive 9.8.2 не подменяет package recipe `1:9.8.1`.

По runtime Gradle `9.8.2` требует JVM 17–27, так что candidate OpenJDK 17 проходит только проверку версии. Активная [матрица платформ Gradle 9.8.2](https://docs.gradle.org/9.8.2/userguide/compatibility.html) включает Ubuntu AArch64, но не Android/Bionic. [Документация file watching](https://docs.gradle.org/9.8.2/userguide/file_system_watching.html) описывает Linux/inotify и перечисленные Linux-дистрибутивы, не Bionic; `--no-watch-fs` отключает watcher, но не доказывает runtime. [Gradle daemon](https://docs.gradle.org/9.8.2/userguide/gradle_daemon.html) — долгоживущий JVM-процесс по умолчанию; `--no-daemon` не проверяет app-private процессы, сокеты и lifecycle. Требуются отдельная проверка целевого runtime и пакета, audit native library loading и `DT_NEEDED`, затем device tests на Bionic: watcher on/off, daemon cleanup и реальная сборка проекта.

Следующие блокеры — доказать совместимость нужных компонентов с ARM64 Android/Bionic и отдельно пройти package/test-feed/device процесс: target package build, audit зависимостей, payload, лицензий и ELF; ephemeral signed test feed и точная APT simulation без установки; затем тест на устройстве. Отдельная assessment-запись и regression gate сверяют новую CI evidence и сохраняют закрытыми все downstream gates: [`gradle-source-bootstrap-assessment.json`](evidence/gradle-source-bootstrap-assessment.json).

## Android SDK/NDK: опубликованные host tools не подтверждают ARM64/Bionic

В pinned source snapshot не найден отдельный recipe для Android SDK Command-Line Tools. Android docs описывают SDK как набор скачиваемых пакетов; один `sdkmanager`/Android CLI не закрывает platform/build-tools и прочие версии SDK. Документация Android Studio сообщает, что Linux с ARM CPU сейчас не поддерживается и требует glibc 2.31+ для Linux. Это не доказывает невозможность запуска каждого одиночного CLI-инструмента, но и не является поддержкой Android/Bionic.

Для NDK r30 официальный download table перечисляет только Linux 64-bit (x86), Windows 64-bit и macOS; Android/ Linux ARM64 host archive не перечислен. У pinned Termux `ndk-sysroot` recipe указан Google NDK Linux archive и уже зафиксирован его SHA-256, но это не превращает host distribution в source recipe или Android/Bionic proof. Нельзя выводить совместимость из того, что целевой ABI приложения — `arm64-v8a`: NDK host ABI и ABI генерируемого APK — разные вещи. См. [Android NDK downloads](https://developer.android.com/ndk/downloads), [SDK package manager](https://developer.android.com/tools/sdkmanager), [Android Studio Linux requirements](https://developer.android.com/studio/install) и [зафиксированный ndk-sysroot recipe](https://github.com/termux/termux-packages/blob/505e06ef0c8dbd7611abfb90e9eb60826dcd01d7/packages/ndk-sysroot/build.sh).

## Что должно пройти до заявления «можно собирать приложения локально»

1. Зафиксировать каждый исходный archive/recipe/patch и builder image; собрать source-buildable Android/Bionic ARM64 host tools и допустимый sysroot. Не переупаковывать официальный Linux-x86 или stock Termux binary как будто он собран под Android.
2. Доказать точные версии, прямые и транзитивные `Depends`/`Pre-Depends`, ABI, license notices, app-private payload paths и ELF loader/provider closure; для повторяемости сравнить независимые сборки.
3. Создать только ephemeral-signed test feed, проверить его подпись и exact dependency closure через APT simulation без установки. Никаких Pages, production feed, production key или публичной release публикации.
4. На ARM64 устройстве установить именно этот test-only feed во встроенный prefix, выполнить Gradle/Clang/SDK/NDK runtime checks и собрать реальный Android APK проектом пользователя; зафиксировать логи, hashes, exit codes и target SDK/ABI. Затем отдельно проверить upgrade и rollback.
5. До получения всех относящихся к claim доказательств оставлять квалификацию и production publication закрытыми; CI source build или APT simulation не заменяют device proof.

Полные pins, hashes, closure fingerprints, Gradle source ZIP inspection, host-only source-build evidence и явно незакрытые gates записаны в [`toolchain-source-readiness-inventory.json`](../toolchain-source-readiness-inventory.json). Валидатор повторяет source-closure inventory, проверяет обе Gradle evidence-записи и asserts, что package/runtime/publication gates остаются закрытыми.
